# Org Flex — Behaviour Spec

This file says what the plugin is supposed to do, so that a future change can be
checked against it. If a change breaks a rule here, either the change is wrong or
this file must be updated in the same commit, on purpose. The invariants in §0
hold in every fork; every other rule is a default a fork may rewrite.

- Each rule has an ID (`VIEW-2`, `CHK-5`, ...) so it can be referred to in commits
  and reviews.
- **Every rule must be testable.** Each one carries **Test:**, naming the
  automated tests that check it (`npm test`), or **Manual:**, saying why only a
  person in Obsidian can check it, or both when a test covers part of it. A
  Manual rule appears in the [manual checklist](#16-manual-checklist) at the end.
  `test/spec.spec.ts` fails if a rule has neither, cites a test that doesn't
  exist, or is Manual without a checklist entry.
- "Known gaps" list things the plugin does *not* do yet. They're written down so
  nobody mistakes them for bugs, or "fixes" them without meaning to.

Code locations are given as files. Line numbers change too often to be useful.
The code is split into `src/org/` (pure Org logic, no editor or Obsidian),
`src/editor/` (CodeMirror extensions), `src/ui/` (Obsidian dialogs, settings tab,
task blocks), `src/features/` (optional parts, PLAT-8), `src/flavour.ts` (workflow
choices, §12a), `src/view.ts` and `src/main.ts`.

## 0. Invariants

Org Flex is a base to be tailored: each user's fork, usually through their own coding agent (`TAILOR.md`), rewrites the rules below to fit how they use Org. Every rule after this section is **today's default** and may be changed, replaced or deleted, together with its tests, in the same change. These four may not: whatever a fork turns into, they hold, and the guard tests named here stay green.

| ID | Rule |
|---|---|
| INV-1 | **Files stay plain Org.** What the plugin writes is Org that Emacs, Orgzly and other Org tools read the same way: no plugin-only syntax, no hidden markers, nothing stored in the file that only Org Flex understands (state of the view lives in the view or in settings). Opening a file and moving through it never changes it; only edits do. A fork that adds an edit writes standard Org for it and tests the exact text it produces. **Test:** "opening a file in the editor and saving it changes nothing". |
| INV-2 | **Phone first.** Anything tappable in the editor goes through `onTap` (`src/editor/state.ts`), so a tap acts without placing the cursor or bringing up the keyboard, and a swipe is a scroll. The only raw listeners are the ones listed, with their reason, in the guard test. The layout rules of `AGENTS.md` (no `height: 100%` on flex children with siblings, one scrolling element on the phone) and full-size touch targets hold. **Test:** "everything tappable in the editor goes through onTap, so a tap never brings up the keyboard", "onTap runs on a still tap or a click, never on a swipe, and keeps focus away", "flex children with siblings never use height: 100%", "on mobile the editor's scroller is the one scrolling element", "bar buttons are full-size touch targets with no gaps between them". |
| INV-3 | **Every rule is testable.** Rules a fork adds or rewrites follow the same form as the rest: an ID, and a Test part naming automated tests or a Manual part with a line in the §16 checklist. **Test:** "every spec rule names its tests or says why it is manual", "every test the spec cites exists", "every manual rule is on the manual checklist, and the checklist names real rules", "the invariants are listed first and each one is guarded". |
| INV-4 | **Command ids are forever.** Users bind hotkeys to command ids, so an id once shipped is never renamed, and never reused for something else; its command may change what it does. New commands get new ids, listed in §9.3 and added to the guard's list of shipped ids. A fork that drops a feature (PLAT-8) drops its commands with it, and moves their ids to the guard's retired list, never to be registered again. **Test:** "every command id ever shipped is still registered or retired, and the spec lists exactly the registered ones". |

## 1. Plugin and platform

| ID | Rule |
|---|---|
| PLAT-1 | Plugin id `org-flex` (`manifest.json`). The id is the plugin's folder name in `.obsidian/plugins/` and must never change, or every user's install and settings are lost. **Test:** "the plugin id is org-flex, and it names the view type". |
| PLAT-2 | Works on desktop and mobile (`isDesktopOnly: false`). `minAppVersion` is `1.5.7` (attachments use `fileManager.getAvailablePathForAttachment`, 1.5.7), so no Obsidian API newer than 1.5.7 may be used without raising it. Example: no `vault.getAllFolders` (1.6.6). **Test:** "the manifest targets desktop and mobile, and no API newer than 1.5.7 is used". |
| PLAT-3 | `.org` files open in the plugin's own view (view type `org-flex`). Obsidian only lists them in the file explorer when *Files and links → Detect all file extensions* is on. Only one plugin can own the `.org` extension, so Org Flex can't be enabled together with another org plugin (such as `orgmode-cm6`); see PLAT-6. **Manual:** needs Obsidian to register the view and the extension. |
| PLAT-4 | The editor is the plugin's own CodeMirror 6 instance, separate from Obsidian's Markdown editor, and CodeMirror is **bundled** into `main.js` rather than borrowed from Obsidian, so it never depends on the versions Obsidian ships. Markdown editor features do not apply to org files unless the plugin builds them. **Test:** "CodeMirror is bundled: only obsidian and electron stay external". |
| PLAT-5 | Build: `npm run build` type-checks (`tsc --noEmit`) and then bundles with esbuild (`esbuild.config.mjs`). The only files deployed to a vault are `main.js`, `manifest.json` and `styles.css`. `npm run deploy` builds and copies them (`scripts/deploy.mjs`) into the vault named by `OBSIDIAN_VAULT` or, failing that, the git-ignored `.deploy.json` (`{"vault": "<path>", "specCopy": "<path in the vault>"}`), and copies `SPEC.md` to `specCopy` when set (or `ORG_FLEX_SPEC_COPY`). No one's own vault path is in the repository. `.npmrc` sets `legacy-peer-deps`, because the `obsidian` typings pin CodeMirror versions the plugin doesn't use. **Test:** "the build type-checks then bundles, and deploys exactly the three artifacts". |
| PLAT-6 | **Another org plugin:** if `.org` is already taken when Org Flex loads, it doesn't fail: a notice that stays until dismissed says which plugin has it ("Orgmode (cm6)" when `orgmode-cm6` is enabled, else the view type that took `.org`, else "another plugin"), to turn that off and then Org Flex off and on again. The rest of Org Flex (commands, Markdown task blocks) still loads. **Test:** "the .org conflict notice names the plugin to turn off". **Manual:** needs two plugins in Obsidian. |
| PLAT-7 | **Releases:** `npm version <patch|minor|major>` bumps `package.json`, copies the version into `manifest.json` and adds it to `versions.json` with the `minAppVersion` (`scripts/version-bump.mjs`), and tags it without a `v` (`.npmrc`). Pushing the tag runs `.github/workflows/release.yml`: tests, build, a check that the tag is the manifest's version, then a **draft** GitHub release with `main.js`, `manifest.json` and `styles.css`, which the community directory installs from. Tags are made from `main` only, never from a personal flavour branch (TAILOR.md). The repository has an MIT `LICENSE`. The manifest's name and description don't say "Obsidian", and the description ends with a full stop. **Test:** "the versions agree, and the manifest is fit for the community directory". **Manual:** the workflow runs on GitHub. |
| PLAT-8 | **Features:** the parts a fork is most likely to keep, change or drop are features (`src/features/`): `backlinks`, `link-update`, `front-matter`, `journal`, `new-note`, `node-find`, `capture`, `attachments`, `task-blocks`. Each is one file, `src/features/<id>.ts`, exporting a `Feature` (`src/features/feature.ts`): its id, the SPEC.md section it owns (which names the file), and what it adds: commands, ribbon icons and events when the plugin loads, editor extensions for each org view, work after a view loads a file, and what its bar buttons do. The core (`src/main.ts`, `src/view.ts`) reaches features only through the list in `src/features/index.ts`, so dropping one is deleting its line there, its file, the pure logic and dialogs only it uses, its spec section and its tests. A bar button belongs to the core (`CORE_BUTTONS`) or to exactly one feature, and shows, in the bar and in settings, only when the core or a listed feature runs it. Editing, folding, zoom, checklists, links, the index and reading mode are core. **Test:** "each feature is one file, listed once, and owns a section of the spec that names it", "only the feature list reaches into a feature, so dropping one stays local", "every bar button is run by the core or by exactly one feature". |
| PLAT-9 | **Tailoring:** the repository is a base to fork. `TAILOR.md` is the procedure a fork's coding agent follows to fit Org Flex to its owner: an interview about how they use Org, starting from their Emacs configuration and files and asking, for each package they use (org-roam, denote, org-attach, org-transclusion, org-capture, org-agenda and whatever else they mention), what it is for, what it leaves in the files and what they need from it in Obsidian; then a proposal, a record of the person in `FLAVOUR.md`, the spec changed first, then code and tests, keeping the §0 invariants. `.claude/skills/tailor/SKILL.md` runs it in Claude Code (`/tailor`), and `AGENTS.md` points every agent to it. `recipes/` holds worked examples. The base's `FLAVOUR.md` describes the base. **Test:** "the tailoring guide, the flavour record and the skill are there, and the guide keeps the invariants", "every recipe says what to ask, and what to change in the spec, the code and the tests". |

## 2. The org file view

`src/view.ts` (`OrgFlexView`)

| ID | Rule |
|---|---|
| VIEW-1 | Opening a file loads its text into a new editor state. The tab title is the file name without extension. **Manual:** needs Obsidian's file loading and tabs. |
| VIEW-2 | Every document change asks Obsidian to save (`requestSave`). Obsidian decides when to write. **Manual:** needs Obsidian's saving. |
| VIEW-3 | Closing the view saves first and destroys the editor afterwards (`super.onClose()` then `destroy()`), because saving reads the editor's text. **Manual:** needs Obsidian's view lifecycle. |
| VIEW-4 | Undo/redo history is CodeMirror's `history()`. Keymap: CodeMirror defaults, history and search keys, and Tab indents. List continuation (CHK-8) has priority over the default Enter. **Test:** "the keymap: Tab indents, Enter continues lists, undo takes edits back". **Manual:** Vim's priority needs Obsidian's Vim setting. |
| VIEW-5 | Vim mode follows Obsidian's *Vim key bindings* setting. It's checked when the editor gains or loses focus, so changing the setting takes effect on the next focus change. Vim has the highest key priority, so in normal mode Enter is Vim's; in insert mode it reaches CHK-8. **Manual:** needs Obsidian's Vim setting. |
| VIEW-6 | Lines wrap. `scrollPastEnd()` is on, so short or fully folded documents can still scroll (mobile requirement, see §13). The caret and selection are the browser's own (no drawn selection), which keeps native selection handles on phones. **Test:** "lines wrap and the selection is the browser's own". **Manual:** scrolling a fully folded file needs a real layout. |
| VIEW-7 | Saving settings applies them to every open org view without reopening it: the shortcut bar and its buttons. (Flavour choices, §12a, are code and apply on reload.) **Manual:** needs open Obsidian views and the settings tab. |
| VIEW-8 | Spellcheck follows Obsidian's *Editor → Spellcheck* setting (on unless it is turned off). The editor sets `spellcheck="true"` (plus `autocorrect` and `autocapitalize` for mobile keyboards) on its content. The setting is read when the file is opened, so a change applies to files opened afterwards. **Test:** "lines wrap and the selection is the browser's own". **Manual:** the underline needs Obsidian's setting. |
| VIEW-9 | **Changes on disk** (Syncthing, Emacs) are applied to the open editor as one edit covering only the part that differs, so the cursor, folds and undo history survive. Undo can take the external change back, like any edit. Opening a different file in the view builds a fresh state. **Test:** "externalChange replaces only the part that differs". **Manual:** needs Syncthing or Emacs writing the file. |

## 2b. Reading mode

`src/editor/reading.ts`, switched in `src/view.ts`. Tests in `test/ui.spec.ts`.

| ID | Rule |
|---|---|
| RD-1 | **Switching:** each org tab has a header icon (`book-open`, "Reading mode"; `pencil`, "Edit", highlighted while reading) and the command `org-toggle-reading` that switch it between editing and reading. A tab starts in editing mode and keeps its mode while it stays open. Switching to reading takes the focus away, so the phone keyboard goes down at once. In reading mode the editor is not editable (`contenteditable="false"`, `.org-reading` on the editor), so tapping text never brings up the keyboard or a cursor; links, folding, zoom, search and the backlinks still work; the shortcut bar and the list grips (CHK-9) are not shown. **Test:** "reading mode: no typing or keyboard, but checkboxes, keywords and dates respond to taps". **Manual:** the header icon and the keyboard need Obsidian on a phone. |
| RD-2 | **Only some edits:** every change to the text is dropped in reading mode (typing, paste, commands, undo) except a checkbox tap (CHK-5), a keyword tap (RD-3), a date from a date tap (RD-4) and changes on disk (VIEW-9). These carry the `allowInReading` annotation. **Test:** "reading mode: no typing or keyboard, but checkboxes, keywords and dates respond to taps". |
| RD-3 | **Tapping a TODO keyword** on a heading toggles it: any open keyword → the first DONE keyword, any done keyword → the first TODO keyword. It never removes the keyword (as ACT-3 does), so it can always be tapped again; a heading without a keyword has nothing to tap. A touch that moved (a scroll) is not a tap, and the cursor doesn't move. **Test:** "tapping a keyword in reading mode toggles open and done, never to none", "reading mode: no typing or keyboard, but checkboxes, keywords and dates respond to taps". |
| RD-4 | **Tapping a date:** each `SCHEDULED:` and `DEADLINE:` timestamp on a planning line is marked `.org-planning-date` with `data-org-date` (always, also when editing); in reading mode it is shown underlined, and tapping it opens the date picker of ACT-4 for that heading and keyword, applied as in ACT-5. `CLOSED:` dates can't be tapped. **Test:** "reading mode: no typing or keyboard, but checkboxes, keywords and dates respond to taps". **Manual:** the date picker is an Obsidian dialog. |

## 3. Parsing and syntax highlighting

`src/org/syntax.ts`. The parser is hand-written and line based: `analyze` classifies every line, `parseInline` parses links and markup on one line. It runs synchronously, so the whole structure is always available. The editor keeps the analysis in the `docInfo` state field (`src/editor/state.ts`), recomputed on every document change. Tests: `test/syntax.spec.ts`.

| ID | Rule |
|---|---|
| PARSE-1 | Supported: headings (any depth) with TODO keyword, priority, title and tags; planning lines (only directly after a heading); drawers, with `:KEY: value` lines in property drawers; blocks (`#+begin_X` … `#+end_X`, any name, with the source language); keyword lines (`#+KEY:`), comment lines (`# `); text markup (bold, italic, underline, verbatim, code, strike-through) including nesting; regular `[[…]]`, angle `<scheme:…>` and plain URL links; markup and links combined. A block or drawer only counts if it is closed before the next heading (headings always win, as in Org); otherwise its first line is plain text. **Test:** "planning only directly after a heading, drawers and blocks need their end line", "headings are stars at column 0 followed by whitespace or the end", "heading keyword, priority, title and tags", "text markup, nested", "links: regular, with description, angle and plain", "markup and links combined; markup never ends inside a link". |
| PARSE-2 | Overlapping markup is resolved into a tree: an opening marker pairs with the nearest valid closing one, so in `*one _two three* four_`, `*one _two three*` is bold and ` four_` is plain. This deliberately differs from Emacs. Markers need Org's borders (whitespace or `-({'"` before, whitespace or punctuation after); the edges of the enclosing markup also count, so `*bold /italic/*` nests. Verbatim and code contents are not parsed. Markup is matched within one line. **Test:** "markup criss-cross becomes a tree, unlike Emacs", "markers need a valid border", "verbatim and code contents are not parsed". |
| PARSE-3 | TODO and DONE keywords come from the flavour (`todoKeywords`, `doneKeywords`, §12a). A keyword is only recognised as the first word of a heading title, exactly as configured. **Test:** "a keyword is only recognised at the start of the title, as configured". |
| PARSE-4 | Source blocks get syntax highlighting for c, c++/cpp, css, html, java, javascript/js, typescript/ts, json, php, python/py, rust, sass, scss and xml (`src/editor/src-highlight.ts`). Each visible block is parsed with that language's Lezer parser; token classes `org-tok-*` map onto Obsidian's `--code-*` colours. **Test:** "the editor renders every feature without errors". |
| PARSE-5 | The parser must never hang on any input. **Test:** "the parser never hangs". |

Not parsed: lists as tree nodes (handled line by line instead, §8), horizontal rules, timestamps as nodes, clocks, footnotes, tables, LaTeX, fixed-width lines, dynamic blocks, markup spanning lines.

## 4. Live preview

`src/editor/preview.ts`. Line decorations are computed for the visible lines on every transaction; hiding a block's last line crosses a line break, so that comes from a state field over the whole document.

| ID | Rule |
|---|---|
| LP-1 | **Markup:** the opening and closing markers (`*…*`, `/…/`, `_…_`, `=…=`, `~…~`, `+…+`) are hidden unless the cursor or selection touches the node. The node gets an `org-text-*` class (`bold`, `italic`, `underline`, `verbatim`, `code`, `strikethrough`); shown markers get `org-markup-marker`. **Test:** "markup markers hide away from the cursor and show as markers when it touches". |
| LP-2 | **Links:** `[[target][desc]]` shows only `desc` and `[[target]]` shows only `target`, unless the cursor touches the link. This holds when `desc` equals `target` too (`[[pkm][pkm]]` shows `pkm`). Rendered links get the class `org-link`; while the cursor touches one it shows raw with `org-link-source`. Angle and plain links are never hidden. **Test:** "tapping a rendered link opens it; a raw link or a swipe doesn't". |
| LP-3 | **Images:** a `[[target]]` link without description whose target ends in `.apng .avif .gif .jpeg .jpg .png .svg .webp` is shown as the image, resolved as file links are (LINK-2), or used as a URL if the vault can't resolve it. A `file:` prefix is allowed. **Test:** "link classification and images" (the extension check). |
| LP-4 | **Blocks:** every line of a block gets the line class `org-block` (plus `org-block-<name>`, `org-block-begin`, `org-block-end`). The `#+BEGIN_` prefix of the first line is hidden unless the cursor is on that line, and the rest of it gets `org-block-header`. The whole last line, with its line break, is hidden unless the cursor is on it. **Test:** "blocks get block line classes and hide their markers away from the cursor". |
| LP-5 | **Headings:** the heading line gets the line classes `HyperMD-header HyperMD-header-N cm-org-level-N`, and the text after the stars gets `org-heading org-heading-N cm-header cm-header-N`. N is capped at 6, so deeper headings look like level 6. **Test:** "headings get level classes, capped at 6, and stars hide when asked". |
| LP-6 | **Heading size** is set on the *line* only (`.cm-line.cm-org-level-N`). The heading text inherits it. Setting it on both makes the `em` sizes multiply. Sizes and colours use Obsidian's `--hN-*` variables, so themes apply. **Test:** "heading sizes are set on the line only, from the theme's heading variables". |
| LP-7 | **Hide stars** (`hideStars`): the leading stars and their space are hidden unless the cursor touches them. All the stars are hidden even when there are more than 6. Shown stars get `org-heading-stars`. **Test:** "headings get level classes, capped at 6, and stars hide when asked". |
| LP-8 | Planning lines, property drawers, other drawers, comments, keyword lines, TODO keywords, priorities and tags get `org-planning`, `org-propertydrawer`, `org-drawer`, `org-comment`, `org-meta-line`, `org-keyword` (plus `org-keyword-todo` or `org-keyword-done`, and `data-keyword`), `org-priority` and `org-tags`; each `SCHEDULED:`/`DEADLINE:` timestamp also gets `org-planning-date` with `data-org-date` (RD-4). These class names are public: user CSS snippets depend on them. **Test:** "planning, drawers, comments, keyword lines, keywords, priorities and tags get their classes". |
| LP-9 | **Completion** (`src/editor/completion.ts`), org-roam style: typing `[[` offers every org ID in the vault **by title**, never by ID (from the index, IDX-1). A note's file-level ID shows as the note's title, with its folder beside it. A heading's ID shows as the heading's title (no keyword, priority or tags; links as their text), with the note's title beside it. Picking one inserts `[[id:<id>][<title>]]`, so it reads as the title in live preview; brackets are dropped from the description. After those come the vault files with no file-level ID (`.org` and `.md` by name without extension, others with it), which insert `[[<file>]]`. Typing `[[id:` still offers every raw `:ID:`, with the file it's in. With Denote, notes, headings and files are offered by their identifier instead (DEN-7). Choosing an entry adds the closing `]]` unless it's already there, and leaves the cursor after the link. **Test:** "titleCompletions lists notes and headings by title, never by ID", "picking a title after [[ inserts an ID link with the title as description", "the link button and ID link command open the list straight away, without typing". |
| LP-10 | **New note from the list:** after `[[`, once something is typed, the list ends with that text and "Create note", unless an entry (note, heading or file) already has exactly that label, ignoring case and surrounding spaces. It comes after every other match, and follows each key typed. Picking it inserts `[[id:<uuid>][<title>]]` (the title trimmed; with Denote `[[denote:<ID>][<title>]]`, DEN-5), leaves the cursor after the link and stays in the file. A note is created in the background at the **vault root**, with the NOTE-5 contents (that UUID as `:ID:`, the title as `#+title`; with Denote, the DEN-4 front matter, named as DEN-5 says). Its file name is the title with each character NOTE-3 refuses replaced by `-` and leading or trailing dots dropped (`Untitled` if nothing is left); if that file exists, ` 2`, ` 3`, … is added, so nothing is overwritten. Not offered after `[[id:`. If the file can't be written, a notice says so. **Test:** "a title nobody has yet can be picked to create the note, linked by its new ID", "the create entry comes after every match and follows the typing", "a note created from the link list gets a clean file name that isn't taken yet". **Manual:** writing the file needs the vault. |
| LP-11 | **Audio:** a `[[target]]` link without description whose target ends in `.3gp .aac .flac .m4a .mp3 .oga .ogg .opus .wav .webm` (a `file:` prefix allowed) is shown, while the cursor is elsewhere, as a small audio player (`.org-audio`, the browser's own controls), resolved as images are (LP-3). Taps on the player play, pause and seek; they don't move the cursor or open the link. Moving the cursor onto the link shows its text. With a description it is an ordinary link. **Test:** "audio links play inline while the cursor is elsewhere, with a loop button; images still show as images", "link classification and images". **Manual:** playing needs a real browser, and that a tap on the player keeps the keyboard down needs a phone. |
| LP-12 | **Loop:** next to each inline audio player (LP-11) is a loop button (`repeat` icon, "Loop", finger-sized on the phone). A tap turns looping on (the button is highlighted, `aria-pressed="true"`, and the audio starts again when it ends) or off, through `onTap`, so it doesn't move the cursor or bring up the keyboard. Looping is not saved: it lasts while the player is on screen. **Test:** "audio links play inline while the cursor is elsewhere, with a loop button; images still show as images". **Manual:** hearing it loop needs a device. |

## 5. Links

`src/editor/preview.ts` (taps and clicks), `src/org/syntax.ts` (`classifyLink`), `src/main.ts` (`openLink`, `findId`).

| ID | Rule |
|---|---|
| LINK-1 | Tapping or clicking a rendered link (or a bare URL the cursor is not in) opens it, without placing the cursor or bringing up the keyboard (the tap is handled on `touchend`/`mousedown` with the default prevented; a touch that moved is a scroll, not a tap). Links with a URL scheme (`https:`, `file:///…`, ...) are external and open with `window.open`, except a relative `file:` link (not starting with `/`), which is a vault file (LINK-2), as Org reads it. `id:` links jump to an org ID. Anything else is a file in the vault. A link shown raw (cursor inside) is edited, not opened. **Test:** "tapping a rendered link opens it; a raw link or a swipe doesn't", "link classification and images". **Manual:** opening the target needs Obsidian. |
| LINK-2 | File links are resolved first relative to the note's folder, as Org does (`file:../attachments/a.jpg` from `notes/n.org` is `attachments/a.jpg`; `.` and `..` worked out, nothing above the vault), when that file exists; then with Obsidian's link resolution: the target as written, then the target plus `.org`. In practice `[[unicorn]]` opens `unicorn.md` when it exists and `unicorn.org` otherwise. A `::search` part is ignored. **Test:** "relative links resolve from the note's folder, and attachments are linked relative to it". **Manual:** uses Obsidian's link resolution. |
| LINK-3 | `[[id:X]]` opens the org file containing a property drawer with `:ID: X`, puts the cursor at that entry (opening any fold around it) and scrolls it to the top. File-level drawers count. An entry that is a heading opens zoomed into it (ZOOM-5). The file is found through the index (IDX-1), waiting up to 2 s for it to be built; only an ID the index doesn't know falls back to reading every `.org` file. **Test:** "VaultIndex finds IDs and follows file changes". **Manual:** opening the file and waiting for the index need Obsidian. |
| LINK-4 | Plain `[[X]]` is never treated as an ID link by the plugin; it is a file link (LINK-2). The Emacs config (org-roam) does treat it as `[[id:X]]`, for indexing and for following. The two agree for older notes, whose file is named after their ID (`X.org` has `:ID: X`). New notes get a UUID (NOTE-3), and the plugin links to notes with `[[id:<uuid>][<title>]]` (LP-9, BL-3), which both resolve the same way, so `[[X]]` is now only for files without an ID. **Test:** "link classification and images". |
| LINK-5 | An ID is the rest of its `:ID:` line, trimmed, so it may contain spaces (`:ID: My Note` is `My Note`), as in Org. An empty `:ID:` is no ID. **Test:** "readNote reads IDs, title and links". |

## 5a. Index and backlinks

`src/org/vault-index.ts` (index and pure functions), `src/editor/backlinks.ts` (the section), `src/main.ts` (vault events, the index), `src/features/backlinks.ts` (feature `backlinks`: refreshing, `linkMention`). Tests in `test/index.spec.ts`. The index itself is core: ID links (LINK-3) and the `[[` list (LP-9) need it with or without this feature.

| ID | Rule |
|---|---|
| IDX-1 | **Index:** the plugin keeps, for every `.org` file, its IDs (with the offset of their entry: 0 for a drawer before the first heading, else the heading's start), its title (`#+title` before the first heading, else the file name), its note links and its text. It is built once the workspace layout is ready and updated on vault create, modify, delete and rename. Each heading ID also keeps the heading's title. It also keeps the Denote identifier in the file name (DEN-2) and the headings' `CUSTOM_ID`s (DEN-7). ID lookups (LINK-3) and link completion by title (LP-9) use it. If two files have the same ID, the first one found wins. **Test:** "readNote reads IDs, title and links", "VaultIndex finds IDs and follows file changes". |

## 5b. Links follow renames

`src/org/rename.ts` (`addMove`, `retargetLinks`), `src/features/link-update.ts` (feature `link-update`: the vault's rename events). Tests in `test/rename.spec.ts`. Obsidian updates links in Markdown notes when a file is renamed, but not in org files; this does it for them. Links the plugin writes to files are always relative to the note (ATT-3), as Org reads them, so Emacs follows them too.

| ID | Rule |
|---|---|
| MV-1 | **When:** renaming or moving a file or a folder (every file in it counts as moved) in Obsidian, by the file explorer, the view header or any other way that goes through the vault. Renames are collected and handled together 300 ms after the last one. A file renamed twice in that time counts as moved from where it started to where it ended, and one renamed back counts as not moved. Changes made outside Obsidian (in Emacs, by sync) aren't seen as renames and change nothing. **Test:** "a batch of renames maps each file from where it started to where it ended". |
| MV-2 | **Which links:** in every `.org` file, a link to a moved file is rewritten to point where it is now. A `[[file:…]]` link counts when it pointed at the file relative to the note, as Org reads it. A plain `[[…]]` link counts when it found the file as LINK-2 does: relative to the note, from the vault root, with `.org` added, or by file name when only one moved file has that name. The description and a `::search` part are kept. A rewritten link is always a `[[file:…]]` link relative to the note, with the file's whole name (a plain `[[unicorn]]` to a renamed `unicorn.org` becomes `[[file:horse.org]]`), so Emacs follows it too. ID links, URLs, absolute (`/…`, `~/…`) paths and links inside the file (`*heading`, `#id`) are never touched. **Test:** "links to a moved file point to its new place, relative to each note", "plain links follow when they found the file by path or by name", "id links, urls, absolute paths and links inside the file are left alone". |
| MV-3 | **A moved note:** when an org note itself moves, its own relative links are rewritten so they still point at the same files from the new folder: every `file:` link, and a plain link that named a file relative to the note; one found by file name elsewhere still is, and stays as it was. Both at once (a folder of notes and their attachments moving together) work out where each is now. **Test:** "a moved note keeps its relative links pointing at the same files", "notes and attachments moved together keep their links". |
| MV-4 | **Writing:** only files whose links change are written, with `vault.process`, so an open note gets the change through VIEW-9 (cursor and folds kept). Every rewritten link is relative to its note. A notice says "Updated links in N org files" when any were. A file that can't be written shows a notice and the others are still done. **Test:** "nothing changes when no link points at a moved file". **Manual:** the rename events need Obsidian. |

| CHK-14 | **Hanging indent:** when a list item's line wraps, its later screen lines start under the item's text (past the grip, bullet and checkbox), not under the bullet, as in Google Docs. Known gaps: Tab/Shift-Tab (VIEW-4) indent or outdent only the selected lines by CodeMirror's indent unit: an item's children don't follow, the indentation doesn't match the bullet above and counters aren't recounted (dragging sideways, CHK-11, does all three); later items in an ordered list aren't renumbered after Enter (only after a drag, CHK-12), there's no `COOKIE_DATA: recursive`, and TODO-based counters on headings with no checkboxes aren't computed.

### 9.2 Actions

A **heading** is a line that starts at column 0 with one or more `*` followed by whitespace or the end of the line. `*bold*` text is not a heading. All actions follow this rule.

|---|---|
| ACT-1 | **Increase level (demote):** on a heading, adds one `*`. On a list item, indents the item instead (ACT-13). On any other line, prepends `* `. | ACT-2 | **Decrease level (promote):** removes one `*`. On a list item, outdents the item instead (ACT-13). On a level-1 heading it removes `* ` and the line becomes plain text. ## 14. Deployment notes

- **Your own vault:** put `{"vault": "~/my-vault"}` in `.deploy.json` (or set `OBSIDIAN_VAULT`) and run `npm run deploy` (PLAT-5). Turn off any other org plugin first (PLAT-3, PLAT-6).
- **Phone:** a vault synced without `.obsidian` (Syncthing ignores, for example) never gets plugin builds on its own. Copy the three files into the phone vault's `.obsidian/plugins/org-flex/` by hand.
- **Releasing:** `npm version patch` (or `minor`), `git push --follow-tags`, then publish the draft release on GitHub (PLAT-7).

## 15. Automated checks

Run before every commit. All of them must pass.

1. `npm test` — all tests pass (132 at the time of writing). `test/dom.spec.ts` mounts the whole editor in happy-dom, which catches decoration errors that pure tests can't.
2. `npx tsc --noEmit --skipLibCheck` — **no errors**.
3. `npm run build` — exits with status 0 (it runs the type-check too).

Every new behaviour gets a rule here and a test, unless it truly needs Obsidian or a phone; then it is **Manual:** with the reason, and gets a line in §16. Logic is kept out of `src/view.ts`, `src/main.ts` and `src/ui/` (which import Obsidian) so it can be tested: `src/editor/setup.ts`, `src/settings.ts` and `src/org/` hold it. `test/dom.spec.ts` and `test/ui.spec.ts` run the editor in happy-dom; `test/packaging.spec.ts` reads the manifest, build config and stylesheet; `test/spec.spec.ts` checks this file.

## 17. Keeping this file current

- A change that alters behaviour updates the matching rule in the **same commit**. A new feature gets a new section or new IDs, and a removed feature has its rules deleted.
- Never reuse a deleted ID for something else; pick a new number.
- Decisions the user made on purpose are recorded with the rule, so they aren't undone later. Examples: the 3-state TODO cycle (ACT-3), no visibility button in the header (BAR-6), `[[X]]` not being an ID link (LINK-4), and the journal header (JRN-2).
